# Barkdown desktop (Electron prototype)

Current delivery queue: [the dependable-workspace plan](../docs/PLAN.md). Start with profile isolation; retain the working prototype and regressions described below.

A working desktop app for the Barkdown product: app-wide documents and conversations on the left, a real assistant in the middle, and typed work tabs on the right. Agents work in folders; the app does not.

## Run it

```sh
cd app
npm install
npm start
```

`npm run dev` opens DevTools as well. Requires Node 22.13+ and a desktop session (Electron 38).

The assistant runs on the sign-ins already on your computer, like T3 Code does:

| Provider | Uses | How it works |
|---|---|---|
| **Claude Code** (default when signed in) | Your `claude` login in `~/.claude` | The Claude Agent SDK drives Claude Code with the chat's working folder as `cwd`, Barkdown's document tools attached as an MCP server, and every edit or command routed through an approval card in the chat. Sessions resume per chat. |
| **Codex** | Your `codex login` in `~/.codex` | The Codex SDK runs its bundled CLI sandboxed to the working folder (`workspace-write`, read-only without a folder) with the same MCP server; file changes are applied in the sandbox and shown as activity and in the review tab. Threads resume per chat. |
| **Claude API key** | A key from Settings or `ANTHROPIC_API_KEY` | Barkdown's own streaming tool loop (`main/agent.js`). Without a key it runs offline and only opens what you name. |

Pick the default under **Settings** (Ctrl+,, Assistant pane); the composer chips switch provider, model and effort per chat. Neither login is copied into Barkdown: the SDKs read the CLI credentials directly.

## What is real

| Area | Implementation |
|---|---|
| Barkpark papers | The document tab for a paper hosts **Barkpark's own editor**, the vendored `<bp-paper-canvas>` Web Component from `api/assets/paper-editor` (`renderer/vendor`, MIT). Blocks come from the connected server; every edit batch (`bp-canvas-ops`) is applied through `POST /v1/plugins/bulldocs/papers/:slug/ops` with the paper's `ifRev`, acknowledged on success, and the server echo is fed back so minted block ids land. A stale revision returns 412 and surfaces as a conflict card (load theirs, or re-apply yours on top); a network failure keeps the batch for retry. Title edits, backlinks and history use the same connection. HTML-only legacy papers render read-only with a one-click conversion to blocks. Papers appear in the sidebar and quick open, and the assistant reads and edits them directly with ids `bp:<slug>`, through revision-fenced operations with Undo. |
| Paper editing (Notion parity) | Improvements made in Barkpark's editor source (`barkdown/editor-quality` branch, merged into Barkpark main via PR #19366; rebuilt and vendored here): a hover gutter with `+` (insert below and open the slash menu) and `⋮⋮` (drag to reorder with a drop line, or click for turn-into / duplicate / move / delete); `Ctrl+Shift+↑/↓` moves a block, `Ctrl+D` duplicates it, `Ctrl+K` opens the link row on a selection; `---` becomes a divider and ``` a code block with the caret inside; `/` also works in an empty list item; strikethrough in the format bubble; the bubble and slash menu carry their Studio styles outside Studio; and a fix so lists created in the canvas save their items (they used to reach the server as empty `bulletList` blocks). Barkdown also rewrites the canvas's insert+move batches so servers older than the `move-block` allowlist accept them. |
| Paper look (Notion) | The vendored canvas ships Barkpark's Studio reading theme (tinted ground, serif display type, a 2px rule above every H2, a §-on-a-hairline divider). `renderer/paper-notion.css` rebinds its tokens for Barkdown: the app ground in light and dark, a sans reading face at 16px/1.5 with 30/24/20 headings, 3px block rows, hairline dividers, a flat code slab, gray callouts, a 52px hover gutter left of the text, and the same neutral surface for the slash menu, format bubble and block menu. A paper whose first block is a heading shows it as the 40px title row (Barkpark derives the paper title from it); otherwise the title input stands in. Status sits in the breadcrumb row. Underline (`Ctrl+U`, bubble button) and Notion's turn-into chords (`Ctrl+Shift+0` text, `1`–`3` headings, `5` bulleted, `6` numbered, `8` code block) were added to the canvas in Barkpark, along with `> ` for a quote block (`> [!note] ` still gives a callout), markdown paste (plain text with headings, lists, quotes, fences or rules lands as blocks), autolinked URLs, and Backspace at the start of a first list item or a quote lifting it to text. Checklists exist now: PortableDoc gained `task: true` on the list block with `checked` per item (server render, BPML, markdown import, all in Barkpark), and the canvas mounts them as native checkboxes with `[ ] ` shorthand, a Checklist slash row, block-menu turn-into and `Ctrl+Shift+4`. Turn-into now persists: a block whose kind changes is replaced on the server (same id) instead of patched, since patches cannot change a block's type. `node tests/editor-gaps.live.mjs` replays all of this against the scratch paper and checks the server's block kinds match the canvas. `node tests/paper-shot.mjs` captures light and dark screenshots for a visual check. |
| Keyboard | `Ctrl+W` closes the active work tab (a menu accelerator, so it also works while a website tab has focus); it never closes the window. On macOS the window closes with `Cmd+Shift+W`. |
| Images in chat (as T3 Code) | Paste an image into the prompt, drop one on the composer, or pick with the attach button. Thumbnails show above the prompt with a remove control and survive switching chats; PNG, JPEG, GIF and WebP up to 20 MB, downsized to 2400px on the long side. Each image is saved under `userData/barkdown/attachments` so chats keep a path, and it travels with the message: base64 image blocks in a streamed user message for Claude Code, `local_image` inputs for Codex, and image blocks ahead of the text for the API loop. Sent images render in the message and open in a lightbox. `node tests/image.live.mjs` sends a solid red PNG to each login and expects the reply to name the colour. |
| Chats know about each other | A side chat's run opens with a `[Workspace context]` note carrying the main conversation's latest exchanges and open tabs; a main chat's run gets a line per side chat with its last question and reply. Every provider also has `list_conversations` and `read_conversation` (MCP tools for Claude Code and Codex, native tools in the API loop) to read any other chat's transcript, including what each reply opened or used. The workspace is written to disk before each run so the note is current. `node tests/sidechat.live.mjs` asks a side chat what the main chat is about on each login. |
| Favorites (replace pins) | Star any work tab (document, paper, website, file, review, terminal or side chat) and it is kept under **Favorites** in the work bar and in quick open. A favorite is a bookmark for the thing the tab showed, not a snapshot of the workspace: open it later from any chat, even after the tab was closed. File, review and terminal favorites reopen in the chat that owns their working folder. Favorites can be renamed and removed from the menu; old pins migrate to a favorite of the tab they focused. |
| Tab names | Double-click a tab to rename it in place. A side chat's name is the side chat's title (it also shows in the pane header and in what other chats see); a document tab's name is the document's title, so renaming it renames the document, local or Barkpark; terminal, review and file tabs take the custom name. |
| Barkpark over direct HTTP | Newer Barkpark servers wrap every response in `result`; the adapter unwraps it, so listing, reading and the connection test see papers again (the library and the assistant both showed none). The document tools (`main/mcp-server.js`) read papers over direct HTTP as well as through the bp CLI; a stored token reaches them as `BARKDOWN_BP_TOKEN`, and published papers read fine without one. Every run's workspace context says which Barkpark it is connected to, the dataset, the mode and whether a token is stored, so the assistant can answer "what are we connected to" without guessing. The sidebar footer shows the paper count and Test connection reports it. |
| Tables in documents | Local documents render GFM tables: `shared/markdown.js` parses a header row, a separator and body rows into Tiptap table nodes and writes them back as pipes, and the document tab mounts Tiptap's table extension. |
| Switching provider keeps the conversation | Each provider session only knows the turns it ran. When a chat switches provider, or comes back to one, the turns that session has not seen travel with the next prompt as "[Earlier in this conversation]" (newest kept whole, oldest dropped past a budget, answers marked with the model that gave them), so Codex can pick up where Claude Code left off and vice versa. The API loop already sends the full history. |
| Settings sheet | `Ctrl+,` opens a two-pane sheet. **General**: theme (System / Light / Dark, previewed as you choose and reverted on Cancel), conversation width, where local data lives with an Open folder button. **Assistant**: the three providers as cards with their sign-in state, the default provider, the model per provider with an "Other model id" entry, and what each provider's own effort default is. **Barkpark**: library toggle, bp CLI or direct HTTP connection with Detect and Test, dataset, and the fenced-writes switch. **Shortcuts**: every keyboard shortcut. **About**: version and runtime. The footer shows when there are unsaved changes; only appearance applies live, everything else lands on Save. |
| Menus and dialogs | Every popup menu opens through one helper (`renderer/src/menus.js`): anchored to the control that opened it (below a toolbar button, above a composer chip), kept inside the window, closed by Escape, a click elsewhere, a resize, or opening another menu; ↑/↓ move through the rows. The provider chip opens a menu like the model and effort chips instead of cycling. Electron has no `window.prompt`, so every question the app asks (page title, favorite name, model id, link address, delete and overwrite confirmations) is an in-app dialog (`renderer/src/dialogs.js`) with the app's controls. `node tests/ui-shot.mjs` captures every menu, the dialog and each settings pane light and dark into `test-results/ui` for a visual check. |
| Work panel opens on demand | With no work tabs in a chat the right panel is collapsed and the conversation takes the width; a panel button in the chat header (or Alt+N, or the assistant opening something) expands it. It collapses again when the last tab closes. |
| Verbose transcript (as Claude Code's app) | Messages are plain: your text in a quiet bubble, the assistant's under a small byline. A reply reads as it happened: thinking in italics, then each step, then the text, in order (`parts` on the reply; older replies without it render steps first). Every step is open by default with a chevron to collapse it, and a step you collapse stays collapsed while the run streams. A command step is labelled with the description the assistant gave ("Read propose and the CLI helpers"), shows the command with names, flags, strings and pipes coloured, and its output in a scrolling box. Edits show a line diff, writes the new lines, Barkdown's own tools a rendered preview. A footer under the reply ticks the elapsed time and what is happening while it runs, then settles to time, tokens, cost and provider ("2m 20s · 3.4k tokens · $0.061 · Claude Code"). Claude Code's thinking blocks, Codex's reasoning summaries and the API loop's thinking arrive as `thinking_delta` events. The change card under a reply lists every file and document it touched with counts and View/Undo. |
| Live activity in Barkdown | While a run works, the composer's indicator and the open step row say what is happening now ("Creating page “Meeting notes”…", "Proposing a change to overview…", "Running npm test…"). Steps for Barkdown's own tools show the page or proposal as it will read (rendered markdown), not JSON. A page the assistant creates lands in the page tree at once, and the change card lists it with View. |
| Terminal tab | A work tab running a shell in the chat's working folder (PowerShell on Windows, the login shell elsewhere) over pipes, so commands, builds and scripts work but full-screen interactive programs do not. Output streams as it arrives, ↑/↓ recall history, Ctrl+C on an empty line restarts the shell. Every command the assistant runs in that chat is mirrored into the tab with its output as it happens. |
| Local documents | Local library in the Electron userData folder (`documents/*.json` plus a `.md` export). Tiptap block editor with slash commands, an attached Types submenu, links, task lists, autosave with revision history, optimistic-rev conflict handling, references, backlinks, related documents, restore. |
| Assistant | Three providers behind one event stream (`main/providers/`): Claude Code via `@anthropic-ai/claude-agent-sdk`, Codex via `@openai/codex-sdk`, and a raw `@anthropic-ai/sdk` loop (`main/agent.js`). Document tools live in a stdio MCP server (`main/mcp-server.js`): list/search/read documents, apply edits directly (with Undo), create documents, show a website or file beside the chat. Each run captures its owner chat and folder; activity events route to that chat's work tabs and respect manual focus. |
| Working folders | Per chat, chosen from the composer. File access is confined to the folder (`main/files.js`). Project editor uses CodeMirror 6 with session buffers, Ctrl+S, and disk-change detection. |
| Code review | `git diff` of the working folder (working tree vs HEAD, or against a chosen commit), rendered per file with hunks. Marking a review never commits. |
| Websites | Electron `<webview>` with address bar, history, and external-open fallback. |
| Side chats | Separate conversation and run inside a work tab, inheriting the parent chat's folder at creation. |
| Pages | The sidebar is a Notion-like page tree, not a flat list: nested pages with expand/collapse, drag and drop to reorder or nest (drop on the edges to reorder, on the middle to nest), hover actions for sub-pages, a context menu (sub-page, move to archive, open beside chat, delete), and breadcrumbs in the document header. Pages can be local documents or Barkpark papers; a paper joins the tree the first time it is seen (notes are papers), and only a deliberate **Move to archive** keeps it in the collapsed **Archive** below, from which any item can be pulled back up. The tree persists with the workspace (`renderer/src/pages.js`). |
| Navigation | Per-chat workspaces, direct document mode, linked-document paths, favorites (below), quick open (Ctrl+K) over tabs, documents, chats, files and actions, Alt shortcuts, an adjustable split that gives the paper 60% by default (the chat is the note’s sidecar). Everything persists to `workspace.json`. |
| Barkpark | Read adapter (`main/barkpark.js`) over the documented `/v1/data/*` endpoints, or through the installed `bp` CLI so no token is copied into Barkdown. Papers appear in the library as read-only and can be imported into the local library. Writes go through the fenced bulldocs ops endpoint and are **off** unless enabled in Settings. |

## What is not there yet

- No T3 Code runtime import, and none planned: the provider adapters are Barkdown's own, built directly on the Claude Agent SDK and Codex SDK.
- Codex edits inside the sandbox are not approval-gated per call (Codex's own `on-failure` policy); Claude Code edits and commands are.
- Local documents still use Tiptap 3 while Barkpark papers use the real Barkpark canvas; they are not yet one editor. Migration to one Paper engine is P2 of the active dependable-workspace plan (docs/PLAN.md); preserve the legacy store until migration proof. The canvas bundle is vendored from the sibling `barkpark-editor` checkout (branch `barkdown/editor-quality`, commit `a5440345c`: table header columns and per-cell alignment, column resize, merged table cells, code highlighting from one tokenizer, IME composition held until commit, the link hover card, text alignment on paragraphs and headings, subscript and superscript, three heading levels carried, the emoji picker, the @ alias, find and replace, the highlight mark, table Tab/Shift+Tab selection, a discard seam for refused saves, and the plain quote block) as an offline fallback; the running app loads the canvas from its connected server, with provenance reported in Settings. [The matrix](../docs/EDITOR-PARITY.md) records regression evidence.
- Barkpark search, related and history go through the adapter but were verified only for list, get, backlinks and history through `bp`.
- Unsaved project buffers live in memory for the session; they are not written to a durable store.
- No packaging beyond `npm run dist` (electron-builder, unsigned).

## Layout

```
main/       Electron main process: window, IPC, documents, files, git, agent, Barkpark adapter, settings
renderer/   index.html, styles.css, src/ (bundled by esbuild into renderer/dist/app.js)
shared/     markdown <-> ProseMirror JSON used by both processes
tests/      unit + Playwright/Electron end-to-end checks
```

The left sidebar resizes by dragging its right edge (160–420 px, limited by the available workspace). The width is saved across restarts. Focus the edge and use arrow keys, or double-click to reset to 200 px.

Assistant document edits now save directly: the visible editor marks the target, shows an agent caret, and reveals the replacement. This is a short presentation of an acknowledged save, not synthetic editor keystrokes. Human input immediately ends the presentation; reduced-motion and hidden panes skip it. Undo is offered for the latest assistant edit only while its revision is still current. Existing pending proposals remain available for manual review; new edits do not create Keep cards.

Cloud papers stay in the collapsed **Cloud archive** until you add them to Pages or import a local copy. Pages order and nesting belong to you and survive refresh/disconnect. The one-time layout migration archives loose cloud entries, preserves nested groups, and keeps the old root order in workspace state for recovery.

In either chat composer, press Up on the first line to recall up to 100 sent messages. Down on the last line moves forward and restores your unfinished draft. History is separate per conversation; restarting while browsing restores the original draft.

Side chats share the full composer and transcript controls with the main chat, including provider/model/effort, images, history, approvals and activity. They appear in Recent chats and quick open, retain a parent link, and can open as a full conversation. Folder and model choices inherit once and can then change independently. Closing a tab or deleting its parent does not delete the side conversation. Older saved side chats are recovered into navigation on load.

## Managed local Barkpark

Settings → Barkpark → Local Barkpark starts a built Windows source checkout with its own Postgres cluster, database-backed readiness, bounded recovery and shutdown on quit. See [setup and limits](../docs/LOCAL-BARKPARK.md). `npm run test:local` exercises the real runtime and Paper editor in isolated temporary data. Existing local notes remain in their current store until the planned migration; profiles and sync are next.
