# C086 — A runtime without a checkout

**Status:** active; opened 2026-09-30, paused behind C087 the same day, resumed 2026-10-01, paused behind C088 and resumed again the same afternoon for the disk image. Stage P5 groundwork, started while [C085](C085-portable-profile.md) waits for the Windows machine ([D-cycle-order](../DESIGN-DECISIONS.md#d-cycle-order--p3-groundwork-starts-while-p2-waits-for-windows-2026-09-29), extended to P5 in [D-packaged-runtime](../DESIGN-DECISIONS.md#d-packaged-runtime--a-release-beside-the-checkout-2026-09-30)).

**Outcome so far:** `Barkdown.app` builds with its runtime inside and starts a profile with nothing else installed: no checkout, no Elixir, no Postgres.

**What exists (`ecf26bc1`):**
- `scripts/build-runtime-release.mjs <checkout>` builds the upstream production release with its own Erlang (90 MB) into `runtime/` and stamps it with the commit it holds. `runtime/` is not committed.
- `app/main/local-barkpark-source.js` accepts a runtime folder that is a checkout or a release. For a release it creates the database, runs the release's migration and seed, and starts the server as its own process group, with a system-only PATH and no distribution port.
- The keys the production server demands are derived from the profile's database password.
- A profile chooses the release the way it chose a checkout: `barkpark.local.source` in its settings.

**Postgres (`74e060a8`):** `scripts/build-runtime-postgres.mjs` builds Postgres 15.18 from the official source (checksum verified), with citext, pg_trgm and pgcrypto, OpenSSL linked statically, and every library addressed relative to the binaries; the build fails if anything links outside the system. `build-runtime-release.mjs --add-postgres` puts it in the release as `postgres/`, and the driver prefers it over the machine's. One exception is patched into the Postgres build and said in the script: libpq's check against exiting calls is relaxed for the two that static OpenSSL brings.

**The application (`1803e0ac`, `b29bce31`):** `scripts/build-mac-app.mjs` builds `Barkdown.app` with the runtime folder under `Contents/Resources/runtime`. In profile mode a profile that has never had a Barkpark connection configured runs on it; New page is then a Paper. The built application uses its own keychain name, because an ad hoc build that reads the development item makes macOS ask every time; a rehearsal runs under a private name and removes its item. [Rehearsal](evidence/C086/live/2026-09-30T16-48-11-085Z-app-packaged/result.json): three checks on the built application. Size: about 1 GB, of which the two agent command-line tools are 510 MB, Electron 254, the runtime 146.

**Proof:** [rehearsal](evidence/C086/live/2026-09-30T16-13-52-486Z-runtime-release/result.json), four checks in Electron with `PATH=/usr/bin:/bin:/usr/sbin:/sbin` and the database server running from the runtime folder: first boot in about 30 seconds, restart in about 5; a note written, found and read after a restart; export and import; a killed app whose runtime is reclaimed. The checkout path still passes its reclaim rehearsal.

**Limits:** one Mac. Release and Postgres were built on it, for macOS 15 on Apple silicon; a Mac without developer tools has not run them. The application is signed ad hoc, not notarized, and needs `--profiles`; an ordinary launch still opens the legacy library. A profile follows its carried runtime when the application moves (unit-tested, not rehearsed with a moved application). No Windows: upstream assembles the release for unix hosts only. An export names the commit from the release's stamp; without git history only the same version imports. The provider truth run against the release is scripted transport, not a live provider.

**Decisions:** [D-packaged-runtime](../DESIGN-DECISIONS.md#d-packaged-runtime--a-release-beside-the-checkout-2026-09-30).

**Notices (2026-10-01):** [docs/third-party/runtime/NOTICES.md](../third-party/runtime/NOTICES.md), generated by `scripts/collect-runtime-notices.mjs`, lists the 86 components a built application carries (the release's Hex packages, Erlang/OTP and Elixir applications, the runtime system, PostgreSQL and the OpenSSL linked into it) with the licence each declares and its text. Six Hex packages ship no text of their own; the standard Apache-2.0 text stands in and the table says so. The Barkpark server itself is private. `THIRD-PARTY.md` points here.

**Provider truth on a Paper (2026-10-01):** the runner that classifies what an assistant did to a note ([`tests/providers.live.mjs`](../../app/tests/providers.live.mjs)) makes its fixture a Paper when the isolated harness supplies a server, and its scripted transport performs the edit through the app's edit service against that Paper. `npm run test:providers-runner:isolated` runs all 25 scenarios, the three in which the edit succeeds included: [result](evidence/C086/live/2026-09-30T22-13-04-398Z-provider-truth-paper/result.json), 25 of 25 against the packaged release in 17 seconds. The isolated harness now takes a packaged release as its source, identified by its stamp. Against the pinned dev checkout the same run was slow and failed differently each time (66 seconds; requests queue behind Phoenix's code reloader, and twice the server stopped answering for a moment), so the release is the runtime for this run.

**First boot (`a38a1d55`, `73282527`, `15f2fca3`):** on every isolated boot of the release the first `bin/barkpark eval` that seeded the database died five seconds into a full `Application.ensure_all_started(:barkpark)`, and the driver's retry hid it (three of three runs; the earlier Electron rehearsal did not record it). The seed booted the whole tree, endpoint included, under eval. The driver now seeds through the release's own `Barkpark.Release.seed()`, which boots without the listener and with the job queue inert, and runs migration and seed without the admission environment, as a managed release refuses a seed boot; the server alone starts with it. A first boot now goes straight from starting to ready. The same rehearsal then showed a second flaw: one slow request under load (a write that took four seconds) failed one health probe, and one failed probe restarted the runtime mid-write. The monitor now needs three missed probes in a row. [Rehearsal on the fixed boot](evidence/C086/live/2026-09-30T22-21-11-396Z-runtime-release/result.json): the four checks pass again.

**Size (2026-10-01):** the two agent tools are 510 MB of the 1 GB. The analysis of using the user's installed Claude Code and Codex instead, what T3 Code does, and the twelve failure modes with their fixes is the paper [The CLI Is Already There](https://guerrilla.barkpark.cloud/papers/the-cli-is-already-there); the recommendation is to drop the bundled binaries in four steps (login-shell PATH hydration, binary path override with a sanity run, tested-with version range, then the drop and rehearsal). Done as C088: the application carries no agent tool and is 456 MB.

**The disk image (`a7e46a86`, 2026-10-01):** `node scripts/build-mac-app.mjs --dmg` writes `app/release/Barkdown-0.6.0-arm64.dmg`, 165 MB, with the application and an Applications link. [Rehearsal](evidence/C086/live/2026-10-01T12-06-09-927Z-app-dmg/result.json): the image mounts read-only, the application is copied out the way a person drags it, the image is detached, and the [packaged rehearsal](evidence/C086/live/2026-10-01T12-06-25-798Z-app-packaged/result.json) passes against that installed copy (first boot, a note, a restart; no agent package inside; 456 MB installed). `npm run test:app-dmg`. The build writes a SHA-256 beside the image and the rehearsal verifies it (A5: artifact integrity); the rehearsal then removes the installed application, checks the user data is untouched, reinstalls from the image and reads the same note back (A5: uninstall preserves user data); then a replacement bundle whose runtime folder is missing is swapped in — it does not start the library, leaves every profile file untouched and says *This copy of Barkdown is missing the runtime it should carry. Reinstall Barkdown from its disk image; your notes and profiles are kept.* — and the previous bundle put back opens the same library (A5: failed-upgrade rollback preserves profiles) — [eight checks](evidence/C086/live/2026-10-01T12-06-09-927Z-app-dmg/result.json). Ad hoc signed and not notarized: on another Mac, Gatekeeper refuses the image until a signature exists; on this one, right-click › Open.

**A5 daily-use checks (2026-10-01):** [`tests/daily-use.live.mjs`](../../app/tests/daily-use.live.mjs) records what one session observes on the carried runtime, as findings rather than verdicts — [9 findings](evidence/C086/live/2026-10-01T11-58-20-421Z-daily-use/result.json). Fine: keyboard-only reaches New page, the work pane, the composer and Send; Settings opens with the shortcut (its button lives in the work bar, which exists only while a work tab is open); the focused composer is indicated by its frame; no sideways scroll at 200% zoom or at 820 px; reduced motion now collapses every animation and transition (the stylesheet rule covered two elements before); a 400-paragraph note writes in 260 ms, opens in 102 ms and saves a typed line in 481 ms. Observed, left as is: at 200% zoom a 1300 px window is 650 CSS px wide, so the layout is the narrow one and New page is behind the collapsed sidebar. `npm run test:daily-use`.

**Release workflow (2026-10-01):** how T3 Code releases, read in full and written up in [Nightly Is the Release Candidate](https://guerrilla.barkpark.cloud/papers/nightly-is-the-release-candidate); the phased proposal for Barkdown is [docs/RELEASE.md](../RELEASE.md), awaiting the owner's go: a release script with the invariants first (nightly and stable channels, checksums from final bytes, notes per channel, no dry run), signing when an identity exists, the updater after that, the CI graph when there is somewhere to run it.

**First release (v0.6.0-nightly.20261001.1, 2026-10-01):** phase 1 of [docs/RELEASE.md](../RELEASE.md) in use. `node scripts/chain.mjs` wrote a passing receipt for `2e78f0e9`; `node scripts/release.mjs nightly` built the image under the nightly version, ran the [install rehearsal](evidence/C086/live/2026-10-01T14-42-48-107Z-app-dmg/result.json) and the [daily-use checks](evidence/C086/live/2026-10-01T14-47-54-413Z-daily-use/result.json) on that image, wrote `SHA256SUMS` from the uploaded bytes, tagged the commit and published [v0.6.0-nightly.20261001.1](https://github.com/FRIKKern/barkdown/releases/tag/v0.6.0-nightly.20261001.1) as a prerelease with the image, the checksums, the receipt and both results. A stable is a nightly's commit promoted (`release.mjs stable`), not yet cut: the signature comes first.

**Release phases 2–3 groundwork (`6d022a13`, `acf4d553`, 2026-10-01):** the build writes the channel's updater feed (`nightly-mac.yml` or `latest-mac.yml`, a zip and its blockmap) beside the image and the release uploads them; with `CSC_NAME` and the three `APPLE_API_*` variables it signs with that identity, hardens and notarizes, otherwise ad hoc without the hardened runtime. The release plan (`scripts/release-plan.mjs`: nightly numbering per day, stable as a promotion of a nightly, previous tag per channel) is tested in `npm run check`. The app (`app/main/updates.js`) checks its channel's feed a minute after launch and every six hours, downloads only when asked, restarts only when asked, and while signed ad hoc refuses the install with the reason; Settings › About shows the state and the one fitting action. [Rehearsal](evidence/C086/live/2026-10-01T20-52-36-144Z-updates/result.json) against a local feed: on, check finds the newer version without downloading, download verifies the digest, install refused with the reason, About shows it. The install step and notarization wait for the signature.
