# Windows loader preparation

The fixed Windows application directory has **200 selected loader API import references in59 of186 physical PE images**. Complete native/import-table comparison covers30,724 symbol references,1,765 ordinary descriptors and63 delayed descriptors. All selected loader references are ordinary imports; other delayed dependencies remain. This is static correspondence, not evidence that a loader call executes or which DLL/path/flags it uses.

[Native capture](loader-imports-03/result.json) reads every fixed image using dumpbin /imports in29612ms. [Independent replay](loader-review-01/review.json) checks372 retained streams, five producer inputs, all29 current source owners, raw table equality and four primary source snapshots in1607ms. Four producer controls and six review controls retain missing/unknown rows, changed ordinary/delayed names, stage/ordinal/near-name handling, alias isolation and raw-byte changes. First [attempt](loader-imports-01/result.json) refused Address of HMODULE; [second](loader-imports-02/result.json) refused a delayed ordinal address. Their native bytes/readers remain. The final fixed dialect handles measured delay metadata and address-prefixed named/ordinal rows; it does not validate ignored native address metadata or become an arbitrary-PE parser.

The application EXE imports SetDefaultDllDirectories; beam.smp.dll imports SetDllDirectoryW. Erlang launcher, BEAM, ExPTY and PostgreSQL have selected load/lookup references. Argon2 has none among the17 selected names. Neither absence nor presence establishes a callsite, policy, flags or dynamically selected module; lookup functions can resolve additional loader APIs at runtime. Separate processes and plugin loading require their own observations. This is why a directory candidate map and system-only PATH are insufficient to prove complete loader resolution.

Primary sources are retained with whole HTML/provenance in [loader-sources](loader-sources-01/review.json):

- [Search order](https://learn.microsoft.com/en-us/windows/win32/dlls/dynamic-link-library-search-order): a full path to one DLL does not fix how its dependencies are located. Loaded modules, API sets, manifests, process policy and directories also matter. Electron-builder terminology alone does not establish Windows package identity or its search-order category.
- [LoadLibraryEx](https://learn.microsoft.com/en-us/windows/win32/api/libloaderapi/nf-libloaderapi-loadlibraryexw): behavior depends on flags; DLL_LOAD_DIR requires a fully qualified filename and affects dependent searches. A static import name contains no flag values.
- [API sets](https://learn.microsoft.com/en-us/windows/win32/apiindex/windows-apisets): names identify contracts resolved through the device schema, not necessarily physical files. A missing same-named file is not by itself a deployment failure; current schema/implementation availability still needs proof.
- [UCRT deployment](https://learn.microsoft.com/en-us/cpp/windows/universal-crt-deployment?view=msvc-170): Windows10/11 use the centrally serviced OS UCRT even when a local copy exists. Copying more candidate DLLs does not substitute for OS/runtime/loader acceptance.
