# Draft — Combined legacy shell/runtime authority adoption

Status: design only, prepared during C009's capture wait. No new app behavior, activation command or UI exists. C009 remains active until its final capture/verification closes. Provisional next bounded cycle ID is coordinator-owned.

## Audited boundaries

C003 `profile-registry.adoptLegacy` accepts a fresh registry, rejects any `local-barkpark` entry, snapshots shell files, preserves unknown compatible fields and selects its new UUID immediately inside that registry. C009 targets an already staged UUID, preserves encrypted credential bytes and original ports, and publishes its runtime descriptor only after cold backup/copy. Neither alone is the default-workspace authority transaction.

C006 opt-in boot currently constructs `<userData>/profile-data`, creates Personal when no registry exists, then initializes service/store and starts runtime reconciliation. An adoption/recovery decision therefore must occur **before registry construction and empty-profile creation**. A missing partially published registry must never be interpreted as permission to seed Personal. Existing nonempty profile-data is not an adoption destination in this first bridge; refuse rather than replace, even if it appears to contain only an empty profile.

Legacy store writers do not honor the new registry lease and the audited boot has no single-instance ownership gate. Copy hashes cannot establish writer exclusion. Explicit adoption must run with old shell writers/provider transports stopped, no open legacy document saves and the managed runtime cleanly stopped. A future trusted-main entry should use an app-instance/adoption lease covering the chosen userData root and make boot consult it. Older binaries do not honor a new lease; that limitation requires a clearly stated closed-old-app prerequisite. Fixtures can prove cooperating-process refusal, not arbitrary external writer exclusion.

## Proposed transaction

1. **Preflight / prepared:** validate source schema/paths/credentials and destination absence; claim userData adoption lease. Persist immutable operation UUID, original source, expected final authority path, source metadata fingerprints and named journal phase. Refuse linked paths, nested/case-aliased roots, unknown source entries, unsupported versions, active owner/pidfile, wrong PG major, encrypted credential unlock failure, external tablespaces and busy retained ports. Never stop an unknown process.
2. **Shell snapshot:** retain original shell bytes under `<userData>/adoption-work/<operation>/shell-original`; manifest includes all allowed entries and unknown compatible fields. Runtime remains at original legacy path. Use a separate sanitized shell snapshot for C003, excluding only the explicitly audited runtime directory. Preserve original full shell backup; do not present the sanitized snapshot as the original source.
3. **Candidate registry:** invoke C003 in `<operation>/candidate-registry` on the sanitized snapshot. Its internal selected UUID is private staging, not desktop authority. Run C009 against original legacy runtime into that same UUID. C009's own source/backup hashes and cold checks stay intact. Candidate may not be loaded by ordinary C006 boot.
4. **Reference conversion / validation:** remap only owned attachment absolute paths that point within the old attachments root to their expected final `<userData>/profile-data/profiles/<uuid>/attachments` paths. Compare mapped file bytes using candidate paths without activating. Preserve external working folders/files as external references and surface inaccessible ones explicitly; never make profile ownership a global working-folder selection. Preserve chat IDs, side-chat parent IDs, tabs, drafts, Pages hierarchy/favorites and document/receipt IDs. Validate workspace shape with C006's repository; pending legacy runs become explicit interrupted state only through an audited conversion, never resume a stale provider process. Preserve original receipts/history where conversion cannot establish semantics.
5. **Ready:** compare shell structured content/reference counts, attachment bytes, source/backup manifests and runtime markers/descriptor. Verify known same-machine encrypted fields through trusted codecs without persisting decrypted values. Recheck source unchanged and stopped. Persist candidate readiness marker with UUID, target root, schema/version and source-manifest hashes. Candidate contains all data required by boot. Do not make a real provider call or start destination runtime during staging if it could mutate the verified copy.
6. **Activating:** durable journal says activating before the final rename. Atomically rename the candidate registry directory to the **absent**, same-volume final profile-data path. This single rename is the authority publication boundary for profile-mode boot. The final registry and readiness marker must agree; no multi-file partial publication is accepted. Preserve operation/shell snapshots outside the renamed directory. Complete journal after verifying final UUID/generation/marker. Windows process-crash ordering is tested; no power-loss guarantee is invented.
7. **Active:** explicit profile-mode boot now loads the published registry. Legacy root is retained, but normal profile mode must not silently fall back there if adopted data disappears. Original-port ownership means legacy and adopted servers are mutually exclusive. Do not rename user-visible documents or reimport duplicate content on retry.

## Recovery and rollback

Prepared/snapshot/candidate-copy interruptions resume the same operation UUID with verified existing bytes; changed source refuses and preserves both versions. If activating and final root is absent, candidate remains staged and legacy authority remains. If final root exists with the expected marker/generation, reconcile active journal without rebuilding or allocating another UUID. A foreign/nonmatching final root fails closed. After active, repeated adoption reports the existing transaction without overwriting edits or revalidating against a subsequently changed legacy source.

Rollback is explicit and offline: refuse active destination runtime/provider ownership, retain edited profile-data by renaming to an operation-specific retired path, record rollback phase, and leave original legacy bytes untouched. Boot recovery must consult the rollback journal before any empty-profile creation. No automatic content merge from adopted edits back to source is claimed. If a rollback process exits after authority retirement but before journal completion, a retry reconciles the retained UUID and never recreates the adopted library. Returning to legacy mode is an explicit startup/authority choice; C006 --profiles must show the recovery state rather than quietly seed Personal.

## Exact disposable integration acceptance

- Start with a realistic legacy shell plus cleanly stopped real runtime: main/side chats, parent IDs, drafts/images, human nested Pages, favorites, local document/proposal/Undo receipt, same-slug Paper and absolute media URL. Preserve original raw hashes and counts.
- Stage and activate twice: exactly one UUID, unchanged original/backup, no duplicate chats/pages/papers, identical IDs and side parents, attachments resolve from final owned path after original attachment directory is temporarily moved to a retained name.
- Boot C006 at final authority; inspect sidebar/tabs/draft/folder; read/edit/reopen original Paper and media. Restart restores the same selected UUID; no background legacy service starts.
- Real child-process exits after each journal publication, per-file copy, candidate-ready, before/after authority rename, before active-journal completion and before/after rollback retirement. Each restart either resumes the same candidate or fails explicitly with retained evidence, never seeds Personal or duplicates a profile.
- Refuse source writers/runtime, foreign final registry, corrupt/truncated journal or marker, missing adopted payload, source mutation during staging, symlink/junction/casing aliases, unsupported schema, credential unlock failure, port collision and wrong PG major. Assert no unrelated process stopped and no original changed.
- Make an adopted-only edit, stop it, roll back and boot legacy: original remains at original revision/media; adopted edited data and both backup manifests remain available. Repeated rollback is idempotent.
- Capture actual adopted-profile UI, not only generic old tours; inspect intermediate activation/recovery states and normal narrow layout. Pair visuals with filesystem/real-server assertions. Complete desktop/root regression before declaring the bridge complete.
