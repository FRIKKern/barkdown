Status: phase 1 in use since 2026-10-01 (`scripts/chain.mjs`, `scripts/release.mjs`); [v0.6.0-nightly.20261003.1](https://github.com/FRIKKern/barkdown/releases/tag/v0.6.0-nightly.20261003.1) (2026-10-03, F1–F7 from the owner's in-app review, cut by hand), [v0.6.0-nightly.20261002.1](https://github.com/FRIKKern/barkdown/releases/tag/v0.6.0-nightly.20261002.1) (2026-10-02, 175 MB — the browser work; cut by hand from a shell receipt because the schedule's launchd runs still lose focus-dependent test steps, see "The schedule"), nightlies [v0.6.0-nightly.20261001.1](https://github.com/FRIKKern/barkdown/releases/tag/v0.6.0-nightly.20261001.1) and [v0.6.0-nightly.20261001.2](https://github.com/FRIKKern/barkdown/releases/tag/v0.6.0-nightly.20261001.2) (the first with the updater feed); signing, real updater installation and Windows installation acceptance remain pending. Learned from T3 Code's release pipeline; the reading and the reasoning are in the paper [Nightly Is the Release Candidate](https://guerrilla.barkpark.cloud/papers/nightly-is-the-release-candidate).

## The idea

A stable release is never a fresh build of `main`. It is the commit of the latest nightly, the one the owner already ran, rebuilt under a stable version and promoted. Verification happens on a real install, not in a staging environment.

## Phase 1 — a release script with the invariants (this Mac)

A machine whose `TMPDIR` is on an external volume refuses `hdiutil attach` there ("Permission denied"), and the disk image rehearsal fails: run the release with `TMPDIR=/tmp/` (found 2026-10-05).

`node scripts/chain.mjs` runs `npm run check` and the full `npm test` on the exact commit at HEAD, stdin closed, and writes a receipt to `.release/chain/<sha>.json` (ignored; the release uploads it). `node scripts/release.mjs <nightly|stable>` then:

1. refuse a dirty tree and a commit without a green full-chain receipt in the cycle evidence;
2. build the runtime stamp, `Barkdown.app` and the disk image (`scripts/build-mac-app.mjs --dmg`);
3. run `test:app-dmg` (install, uninstall, reinstall, failed-upgrade rollback) and `test:daily-use`;
4. write `SHA256SUMS` from the final bytes about to be uploaded;
5. generate notes against the previous tag in the same channel, with the cycle record's evidence links;
6. tag that commit and create the GitHub Release with `gh`: nightly as `vX.Y.Z-nightly.<date>.<n>` (prerelease, never latest), stable as `vX.Y.Z` on a nightly's commit (latest, `--from <nightly tag>` to choose one). `app/package.json` holds the *next* stable version; after a stable release it moves to the next patch on `main`. The rehearsal results and the chain receipt are uploaded beside the image.

No dry run: every run of the script is a real release. The script says so.

## The schedule on GitHub (since 2026-10-27)

`.github/workflows/release.yml` runs on GitHub's hosted `macos-latest` (free for this public repository), the way T3 Code releases: every two hours it asks `release.mjs nightly --if-due --due-only` whether main has moved and six hours have passed, and only then builds Postgres (cached), the Barkpark runtime at the pin from source (Homebrew's Erlang; the libraries it links are carried, `scripts/runtime-macho.mjs`), runs `release.mjs` with the full chain, the rehearsals and the publish. A stable is dispatched by hand and promotes the newest nightly's commit (or `from`). The runner is unattended like the launchd schedule below (`BARKDOWN_TEST_FOREGROUND`, `BARKDOWN_MOCK_KEYCHAIN`) and its display is set to 1920×1080. Apple silicon only so far; signing switches on with the Developer ID secrets (`CSC_LINK`, `CSC_KEY_PASSWORD`, `APPLE_API_KEY`, `APPLE_API_KEY_ID`, `APPLE_API_ISSUER`). The workflow had pointed at a self-hosted runner that was never registered: from 5 to 27 October every scheduled run queued for hours and was cancelled, and no nightly was cut.

## The schedule on this Mac (since 2026-10-02, now a fallback)

A launchd agent runs `scripts/nightly-tick.sh` every two hours (`node scripts/nightly-schedule.mjs install | remove | status`; the agent is `~/Library/LaunchAgents/no.guerrilla.barkdown.nightly.plist`, written from `scripts/launchd/`). The schedule works in a checkout of its own at `~/Library/Application Support/Barkdown/nightly` (cloned and brought to `origin/main` by `install`, with its dependencies and a copy of the runtime folder): a background process is denied `~/Documents` by macOS privacy protection — the agent's first eight runs on 2026-10-02 died on *can't open input file* — and a release should not run inside the checkout a person is working in. The schedule's first day (2026-10-02): the agent fired on time every two hours; its runs died on `~/Documents` privacy protection (own checkout now), then a `%20` in the checkout path (fixed), then the keychain (`BARKDOWN_MOCK_KEYCHAIN=1`), then a lost double-click (the journey retries, the chain retries its test step once), then focus-dependent steps (`BARKDOWN_TEST_FOREGROUND=1`, not yet verified by a scheduled run). Until a scheduled run goes green end to end, a nightly is cut by hand: chain in a clean worktree, copy the receipt, `node scripts/release.mjs nightly` — fifteen minutes. The tick sets `BARKDOWN_MOCK_KEYCHAIN=1`: a launchd process cannot answer a keychain prompt, and without the keychain Chromium cannot read back the cookies it wrote, so the chain's Electron runs use Chromium's mock keychain (a person's own Barkdown never does). A tick runs only when nobody is at the Mac (no keyboard or mouse input for ten minutes, read from `IOHIDSystem`) and no other `chain.mjs` is running — on 2026-10-03 the scheduled chain overlapped the developer's chains and stole focus from the person using Barkdown, and both chains went flaky. A tick does nothing unless that checkout is idle — on `main`, no tracked changes, and `origin/main` fast-forwards — then runs `release.mjs nightly --if-due --chain`: not due (no new commits, or the last nightly is under six hours old) means exit 0 and one log line; due means the chain runs first when the commit has no receipt (about twenty minutes of Electron windows opening and closing on this Mac), and the nightly is cut from a passing receipt. An unattended chain gets one more try at its test step (`chain.mjs --retry-once`, and the receipt keeps the first attempt under `firstTest`); a commit whose chain failed twice is not retried; the next commit gets its own chain. Log: `.release/nightly-tick.log`. The GitHub Actions workflow (`.github/workflows/release.yml`) has the same cron for the day a self-hosted runner exists; until then this agent is the schedule.

## Phase 3 — the updater

Built in (`app/main/updates.js`, Settings › About): `electron-updater` with the GitHub provider against the running channel's feed (`nightly-mac.yml` for a nightly build, `latest-mac.yml` for a stable), which every release now carries beside the image with the zip and its blockmap. A background check a minute after launch and every six hours; one click to download; one to restart; never on its own. While the application is signed ad hoc the install is refused with the reason (Squirrel.Mac validates the new bundle's signature against the running one), so the step is exercised only after phase 2. `BARKDOWN_UPDATE_URL` points the updater at any static feed for a rehearsal (`npm run test:updates`). The owner made the repository public on 11 October 2026, so repository visibility no longer requires a read token for the release feed. This does not establish signed updater installation or recovery. The pre-install snapshot is implemented in `app/main/main.js` and `updates.js`: when a local runtime is enabled and portability is available, export the selected profile and save a marker; a failed export refuses installation. Without that local runtime the snapshot returns no copy. This is neither an all-profile backup nor automatic restoration after a failed upgrade. Real signed install and failed-upgrade recovery still need acceptance proof; fake-updater unit tests only prove orchestration.
